# Feature Specification: 同步任务多项优化

**Feature Branch**: `013-sync-optimizations`  
**Created**: 2026-01-15  
**Status**: Draft  
**Input**: User description: "新增多个小优化：清理空任务时检查上次任务状态、同步时展示检查中的文件数、传输进度区分上传下载、任务完成时toast提醒、允许禁用任务、缓存文件大小不正确、概览卡片数据分离加载"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 任务完成时 Toast 提醒 (Priority: P1)

用户在执行同步任务时，希望在任务完成后能够及时收到通知提醒，无论任务是成功、失败还是被取消，以便快速了解同步结果而无需持续关注界面。

**Why this priority**: 这是最直接影响用户体验的功能，让用户无需持续盯着界面等待同步完成，提升使用效率和体验。

**Independent Test**: 可通过启动任意同步任务并等待完成来独立验证，完成时应弹出相应状态的 Toast 通知。

**Acceptance Scenarios**:

1. **Given** 用户启动了一个同步任务，**When** 任务执行成功完成，**Then** 系统显示成功样式的 Toast 通知，包含任务名称和完成状态
2. **Given** 用户启动了一个同步任务，**When** 任务执行失败，**Then** 系统显示错误样式的 Toast 通知，包含任务名称和失败提示
3. **Given** 用户启动了一个同步任务，**When** 任务被用户取消，**Then** 系统显示警告样式的 Toast 通知，包含任务名称和取消提示
4. **Given** 用户在连接详情页面，**When** 该连接下的任务完成，**Then** 应显示 Toast 通知
5. **Given** 用户在其他页面（非当前任务所属连接），**When** 任务完成，**Then** 应显示 Toast 通知（全局通知）

---

### User Story 2 - 传输进度区分上传下载 (Priority: P1)

用户在查看正在传输的文件时，希望能够区分当前文件是正在上传还是正在下载，以便更清楚地了解数据流向。

**Why this priority**: 这是用户理解同步行为的核心信息，特别是在双向同步场景下尤为重要。

**Independent Test**: 可通过启动包含上传和下载的同步任务来验证，传输列表应使用不同图标或标签区分上传和下载。

**Acceptance Scenarios**:

1. **Given** 用户正在执行单向上传任务，**When** 查看活跃传输列表，**Then** 每个传输项显示上传图标或标签
2. **Given** 用户正在执行单向下载任务，**When** 查看活跃传输列表，**Then** 每个传输项显示下载图标或标签
3. **Given** 用户正在执行双向同步任务，**When** 查看活跃传输列表，**Then** 每个传输项根据实际传输方向显示对应的上传或下载图标

---

### User Story 3 - 同步时展示已检查的文件数 (Priority: P2)

用户在同步任务运行时，希望能看到当前已完成检查（扫描）的文件总数，以便了解同步进度的完整情况，特别是在同步大量文件时。

**Why this priority**: 增强用户对同步进度的感知，尤其在同步开始阶段（扫描文件）时提供反馈。

**Independent Test**: 可通过启动大目录同步任务来验证，进度显示区域应展示"已检查 X 个文件"的信息。

**Acceptance Scenarios**:

1. **Given** 用户启动了一个同步任务，**When** 系统正在扫描文件，**Then** 进度区域显示当前已完成检查的文件总数
2. **Given** 同步任务正在运行且文件检查完成，**When** 用户查看进度，**Then** 已检查文件数显示为扫描完成的总数
3. **Given** 同步任务正在运行，**When** 没有文件需要传输（所有文件已同步），**Then** 仍显示已检查的文件总数

---

### User Story 4 - 允许禁用任务 (Priority: P2)

用户希望能够临时禁用某个同步任务，使其不再响应定时触发或实时触发，但保留任务配置以便将来重新启用，而无需删除后重新创建。

**Why this priority**: 提供更灵活的任务管理能力，避免用户为了暂停同步而删除任务配置。

**Independent Test**: 可通过禁用带有定时触发的任务来验证，禁用后任务不应自动执行，手动运行仍可正常工作。

**Acceptance Scenarios**:

1. **Given** 用户有一个启用状态的任务，**When** 用户点击禁用图标按钮，**Then** 任务状态变为禁用，任务状态图标变为禁用状态图标
2. **Given** 任务处于禁用状态且配置了定时触发，**When** 到达触发时间，**Then** 任务不会自动执行
3. **Given** 任务处于禁用状态且配置了实时同步，**When** 文件发生变化，**Then** 任务不会自动执行
4. **Given** 任务处于禁用状态，**When** 用户手动点击运行按钮，**Then** 任务仍可正常执行
5. **Given** 任务处于禁用状态，**When** 用户点击启用图标按钮，**Then** 任务恢复正常状态，定时和实时触发重新生效

---

### User Story 5 - 清理空任务时保留最新记录 (Priority: P3)

当启用了自动清理空任务（`auto_delete_empty_jobs`）时，系统应确保始终保留该任务的**最新一条**执行记录（即使它是没有任何文件变动的空任务）。如果新任务完成时发现前一条记录也是空任务，则删除旧的空任务记录。

**Why this priority**: 优化清理逻辑，既能让用户通过最新的时间戳确认系统正在正常运行，又能防止大量无变动的历史记录堆积。

**Independent Test**: 可通过配置 `auto_delete_empty_jobs = true`，连续执行两次无变动的同步任务，观察任务历史中是否仅保留了最后一次的记录。

**Acceptance Scenarios**:

1. **Given** `auto_delete_empty_jobs = true`，**When** 当前任务 (Job B) 完成且无文件变动，且前一个任务 (Job A) 也是无变动的成功记录，**Then** 系统删除 Job A，保留 Job B
2. **Given** `auto_delete_empty_jobs = true`，**When** 当前任务 (Job B) 完成且无文件变动，但前一个任务 (Job A) 是失败或被取消的记录，**Then** 系统保留 Job A，同时也保留 Job B
3. **Given** `auto_delete_empty_jobs = true`，**When** 当前任务 (Job B) 完成且有文件变动，且前一个任务 (Job A) 是无变动的空记录，**Then** 系统删除 Job A，保留 Job B
4. **Given** `auto_delete_empty_jobs = false`，**When** 任务完成，**Then** 所有历史记录均正常保留，不执行任何自动删除操作

---

### User Story 6 - 修复缓存数据库大小统计不正确 (Priority: P3)

用户查看缓存状态时，显示的缓存数据库大小不准确。原因是 SQLite 在 WAL 模式下会生成 `-wal`（Write-Ahead Log）和 `-shm`（Shared Memory）附属文件，但当前的大小统计只计算了主数据库文件 `.db` 的大小，未包含这些附属文件。

**Why this priority**: 这是一个 bug 修复，影响用户对缓存占用空间的准确了解。

**Independent Test**: 可通过查看缓存状态卡片显示的数据库大小，与文件系统中 `.db` + `.db-wal` + `.db-shm` 三个文件的总大小进行对比验证。

**Acceptance Scenarios**:

1. **Given** metacache 数据库存在 WAL 和 SHM 附属文件，**When** 系统计算缓存数据库大小，**Then** 返回的大小包含主数据库文件、WAL 文件和 SHM 文件的总大小
2. **Given** metacache 数据库只有主文件（无 WAL/SHM），**When** 系统计算缓存数据库大小，**Then** 返回主数据库文件的大小
3. **Given** 用户查看缓存状态卡片，**When** 显示缓存大小，**Then** 显示的大小与文件系统中所有相关文件的总大小一致

---

### User Story 7 - 概览卡片数据分离加载 (Priority: P2)

用户在查看连接概览页面时，存储使用卡片和缓存状态卡片的数据目前是一起获取返回的。由于存储使用数据需要调用远程云端 API（rclone about），获取速度较慢，导致本地缓存状态数据（获取速度很快）也无法及时展示。用户希望这两个卡片的数据能够分开加载，使缓存状态卡片能够快速展示，而存储使用卡片可以异步加载。

**Why this priority**: 这是用户体验优化，解决页面加载时的等待感，让用户能更快看到可用信息。

**Independent Test**: 可通过打开连接概览页面来验证，缓存状态卡片应在 1 秒内展示数据，而存储使用卡片可以稍后加载完成。

**Acceptance Scenarios**:

1. **Given** 用户进入连接概览页面，**When** 页面开始加载，**Then** 缓存状态卡片应独立加载并快速展示数据，不受存储使用卡片加载速度影响
2. **Given** 用户进入连接概览页面，**When** 存储使用数据正在加载中，**Then** 存储使用卡片应显示加载状态指示器
3. **Given** 用户进入连接概览页面，**When** 缓存状态数据已加载完成但存储使用数据仍在加载，**Then** 缓存状态卡片已正常展示数据，存储使用卡片仍显示加载状态
4. **Given** 用户进入连接概览页面，**When** 存储使用数据加载失败，**Then** 存储使用卡片应显示错误状态，缓存状态卡片不受影响

---

### Edge Cases

- 任务完成时用户已关闭浏览器标签页？Toast 通知不显示（预期行为，无持久化通知需求）
- 禁用的任务在应用重启后状态是否保持？禁用状态应持久化到数据库
- 双向同步中同一文件先删除后创建如何显示方向？应根据最终操作显示
- WAL 或 SHM 文件不存在时如何处理？仅统计存在的文件大小，不报错
- 存储使用数据加载超时如何处理？应显示超时错误状态，允许用户手动重试
- 连接不支持配额查询（如本地文件系统）时如何处理？存储使用卡片应显示"不支持"状态或隐藏

## Requirements *(mandatory)*

### Functional Requirements

**任务完成通知**
- **FR-001**: 系统必须在任务执行完成时向用户显示 Toast 通知
- **FR-002**: Toast 通知必须根据任务状态（成功/失败/取消）显示不同的样式（success/error/warning）
- **FR-003**: Toast 通知必须包含任务名称和完成状态描述（建议：成功时显示“同步成功”，失败时显示“同步失败”，取消时显示“已取消”）
- **FR-004**: 通知必须在任务完成后 1 秒内显示，无论用户当前在哪个页面
- **FR-024**: 当多个任务同时完成时，Toast 通知应堆叠显示，不应互相覆盖或只显示最后一个

**传输方向区分**
- **FR-005**: 系统必须在传输进度事件中包含传输方向信息（上传/下载）
- **FR-006**: 前端必须根据传输方向显示相应的箭头图标（↑上传/↓下载），不附加文字标签
- **FR-007**: 双向同步时，每个文件的传输方向必须根据实际操作正确显示

**检查文件数显示**
- **FR-008**: 系统必须在同步进度中提供已检查的文件总数信息
- **FR-009**: 前端必须在任务状态卡片中以单独一行显示当前已检查的文件总数
- **FR-010**: 已检查文件数量必须实时更新

**任务禁用功能**
- **FR-011**: 系统必须为任务添加"启用/禁用"状态字段
- **FR-012**: 用户必须能够通过任务列表中的图标按钮（与运行、编辑等按钮并列）切换任务的启用/禁用状态
- **FR-013**: 禁用的任务必须不响应定时触发
- **FR-014**: 禁用的任务必须不响应实时文件变更触发
- **FR-015**: 禁用的任务必须仍可通过手动方式运行
- **FR-016**: 任务的启用/禁用状态必须持久化存储

**空任务清理优化**
- **FR-017**: 当 `auto_delete_empty_jobs = true` 时（系统默认值），系统必须在当前任务 (Job N) 完成后立即检查其前一个历史记录 (Job N-1)，其中 Job N-1 定义为同一任务按完成时间排序的上一条已完成记录（状态不限）
- **FR-018**: 如果 Job N-1 是“空任务”（执行成功且无任何文件传输/删除/重命名等变动），系统必须将其删除，**无论当前 Job N 是否有文件变动**
- **FR-019**: 如果 Job N-1 不是空任务（如失败、取消或有实际变动），系统必须保留 Job N-1
- **FR-025**: 始终保留当前刚完成的任务 (Job N) 的记录

**缓存数据库大小统计修复**
- **FR-020**: 系统计算缓存数据库大小时必须包含主数据库文件（`.db`）的大小
- **FR-021**: 系统计算缓存数据库大小时必须包含 WAL 文件（`.db-wal`）的大小（如果存在）
- **FR-022**: 系统计算缓存数据库大小时必须包含 SHM 文件（`.db-shm`）的大小（如果存在）
- **FR-023**: 当 WAL 或 SHM 文件不存在时，系统应正常返回已存在文件的总大小，不报错

**概览卡片数据分离加载**
- **FR-026**: 缓存状态卡片数据必须独立于存储使用卡片数据进行获取，不因存储使用数据获取缓慢而被阻塞
- **FR-027**: 存储使用卡片在数据加载过程中必须显示加载状态指示器
- **FR-028**: 存储使用卡片加载失败时必须显示错误状态，并提供用户友好的错误提示
- **FR-029**: 缓存状态卡片的加载和展示不受存储使用卡片加载状态的影响
- **FR-030**: 存储使用数据和缓存状态数据应使用独立的 API 请求获取

### Key Entities *(include if feature involves data)*

- **Task**: 同步任务实体，新增 `enabled` 布尔字段表示启用/禁用状态
- **TransferItem**: 传输项，新增 `direction` 字段（UPLOAD/DOWNLOAD）表示传输方向
- **JobProgressEvent**: 任务进度事件，新增 `filesChecked` 字段表示已检查的文件数

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 任务完成后 1 秒内显示 Toast 通知
- **SC-002**: 用户能够在 2 次点击内完成任务的启用/禁用切换
- **SC-003**: 传输列表中 100% 的传输项正确显示上传/下载方向
- **SC-004**: 同步过程中实时显示已检查的文件数量，更新延迟不超过 1 秒
- **SC-005**: 禁用任务后，定时和实时触发 100% 不会执行该任务
- **SC-006**: 缓存数据库大小统计包含所有相关文件（.db + .db-wal + .db-shm），与文件系统实际占用 100% 一致
- **SC-007**: 当上次任务失败时，空任务保留率为 100%
- **SC-008**: 缓存状态卡片在页面加载后 1 秒内展示数据，不受存储使用数据加载速度影响
- **SC-009**: 存储使用卡片在数据加载过程中 100% 显示加载状态指示器

## Clarifications

### Session 2026-01-15

- Q: Toast 通知自动消失时间? → A: 使用项目默认值，不额外指定

### Session 2026-01-16

- Q: 禁用任务的UI控件类型? → A: 图标按钮
- Q: 禁用任务图标按钮的位置? → A: 任务列表中与运行、编辑等按钮并列
- Q: 传输方向的视觉区分方式? → A: 仅图标（上传/下载箭头）
- Q: 已检查的文件数展示位置? → A: 任务状态卡片中单独一行
- Q: 禁用任务的视觉标识方式? → A: 任务状态展示为不同图标
- Q: 多个任务同时完成时的 Toast 显示方式? → A: 堆叠显示 (Stacked)
- Q: 空任务清理的具体逻辑? → A: 滚动替换。若当前任务完成且开启自动清理，则检查并删除“上一个”空任务，从而始终保留最新的执行记录。
- Q: Job N-1 如何确定? → A: 同一任务按完成时间排序的上一条已完成记录（状态不限）
- Q: 概览卡片数据分离的实现方式? → A: 将存储使用数据和缓存状态数据拆分为独立的 API 请求，前端分别调用并独立渲染
